# План: параллельный запуск сценариев внутри одного процесса (asyncio-конкурентность)

## Статус
Черновой дизайн, реализация — внешним плагином (без изменения ядра `vedro`, за
исключением точечных monkey-patch/переопределений через существующий DI-механизм).

## Цель
Дать возможность одному процессу `vedro run` выполнять несколько сценариев
"одновременно" за счёт кооперативной asyncio-конкурентности (`await`-переключения),
без честного распараллеливания по CPU (GIL остаётся один). Выигрыш — на
I/O-bound сценариях (сеть, диск, sleep, ожидание внешних сервисов).

Должно быть совместимо с `Slicer` (межпроцессное/межмашинное разбиение): один
"воркер" Slicer'а получает свою часть сценариев и уже её крутит конкурентно
через этот раннер. Т.е. многоуровневая схема:
`N машин (Slicer) × M конкурентных сценариев (этот раннер) на машину`.

## 1. Точка встраивания

Ядро явно предоставляет DI-контейнер `Registry.ScenarioRunner` (`Factory[ScenarioRunner]`)
с методом `.register(resolver, registrant)`. Именно так штатно поступает
`DryRunnerPlugin` (`vedro/plugins/dry_runner/_dry_runner_plugin.py`), подменяя
раннер на `on_arg_parsed`. Это единственный путь для внешнего плагина заменить
исполнитель сценариев, не трогая `vedro/_config.py`.

Примечание: в `vedro/_config.py` есть комментарий, что кастомные раннеры
депрекейтятся к v2.0, а `run_command.py` кидает `DeprecationWarning`, если
`runner` не является `MonotonicScenarioRunner`/`DryRunner`. Это не блокирует
работу в текущей ветке 1.x, но означает, что решение нужно рассматривать как
временное/версионно-зависимое и закладывать миграцию при выходе v2.

Состав внешнего пакета (условно `vedro-parallel-runner`):
- `ParallelRunner(PluginConfig)` + `ParallelRunnerPlugin(Plugin)` — CLI-флаг
  `--parallel N` (0/1 = выключено, поведение как сейчас).
- `ParallelScenarioRunner(ScenarioRunner)` — сам исполнитель.
- Набор "патчей совместимости" (см. раздел 3) для функциональных плагинов
  ядра, которые не переживут конкурентность как есть.

## 2. Архитектура `ParallelScenarioRunner`

Базово переиспользует код `MonotonicScenarioRunner` (наследование или
композиция) для `run_step`/`run_scenario` — эта часть (выполнение шагов одного
сценария) остаётся последовательной и без изменений. Меняется только верхний
уровень — `run()`/`_run_scenarios()`:

- Ограничитель конкурентности: `asyncio.Semaphore(N)`, где `N` — значение
  `--parallel`.
- Забор сценариев из `scheduler` (async-итератор) выполняется **последовательно
  в одном месте** (сам `scheduler.__anext__` не потокобезопасен и не рассчитан
  на конкурентный доступ), но каждый добытый сценарий немедленно оборачивается
  в `asyncio.Task` и кладётся в пул воркеров, ограниченный семафором.
- Использовать `asyncio.TaskGroup` (3.11+) вместо ручного `gather`, чтобы при
  исключении в одной задаче остальные автоматически отменялись — это нужно для
  корректной работы `--fail-fast`/`Interrupter` (см. раздел 3, пункт 8).
- Результаты каждого сценария складываются в `dict[unique_id, list[ScenarioResult]]`
  по мере завершения задач (а не по признаку "соседства" в потоке, как в
  `MonotonicScenarioRunner._run_scenarios`), финальная агрегация через
  `scheduler.aggregate_results(...)` — как только все повторы конкретного
  `unique_id` завершены.
- Порядок формирования отчёта (`report.add_result`) — по завершению, а не по
  порядку обнаружения; если нужен стабильный порядок в отчёте — буферизовать
  результаты и досортировать перед финальным выводом (актуально прежде всего
  для консольного репортера, см. пункт 7).

## 3. Обязательные патчи (совместимость)

| № | Компонент | Проблема | Патч |
|---|---|---|---|
| 1 | `MonotonicScenarioRunner.run_scenario()` — `os.chdir(scenario._project_dir)` | Глобальный `cwd` процесса; гонка между параллельно выполняющимися сценариями | Убрать per-scenario `chdir`, делать один `chdir` на процесс при старте (в норме `project_dir` общий для всех сценариев прогона) |
| 2 | `OutputCapturer` / `CapturedOutput` (`redirect_stdout`/`redirect_stderr`) | Подмена глобального `sys.stdout/stderr`; при чередовании задач вывод "перетекает" между сценариями | Заменить на capture, завязанный на `contextvars`/`asyncio.current_task()`: каждый таск получает свой буфер, стандартные потоки не подменяются глобально |
| 3 | `functioner._step_recorder.get_step_recorder()` — глобальный синглтон | Все fn-сценарии, идущие параллельно, пишут шаги в один и тот же список | Recorder должен создаваться на таск (contextvar) либо явно передаваться как параметр вглубь вызова, а не браться из глобального геттера |
| 4 | `deferrer._queue` / `_global_queue` — глобальные `deque` на уровне модуля | `on_scenario_run` чистит общую очередь — конкурентный сценарий теряет свои `defer()` | Переделать очередь на `ContextVar` (своя очередь на asyncio-task) либо словарь, ключ — `scenario.unique_id` |
| 5 | `MonotonicScenarioRunner._run_scenarios` — группировка по "соседству" (`prev_scenario.unique_id != scenario.unique_id`) | При параллельном выполнении порядок завершения не гарантирован — соседства нет | В `ParallelScenarioRunner` агрегировать явно по `dict[unique_id]`, а не по порядку потока |
| 6 | `Repeater`/`Rerunner` (`scheduler.schedule()`) | Семантика "N попыток подряд"/"большинство из reruns" неявно опирается на последовательный порядок | Отдельное тестирование; при необходимости — не запускать повтор `unique_id`, пока не завершены предыдущие его копии |
| 7 | `RichReporter.on_scenario_run` — спиннер и построчная печать "текущего" сценария | Репортер расчитан на один активный сценарий в моменте; при параллели вывод разных сценариев будет чередоваться | Отдельный parallel-aware репортер: буферизация вывода на сценарий, атомарная печать блоком по завершении (аналог pytest-xdist); либо отключение live-spinner при `--parallel` |
| 8 | `Interrupter` (`--fail-fast`, `--fail-after-count`) — останов через всплытие исключения `Interrupted` по цепочке `await` | В monotonic-раннере исключение "проедает" весь стек await и останавливает всё; в параллельном варианте есть другие уже запущенные задачи | Использовать `asyncio.TaskGroup` (автоматическая отмена сиблингов при исключении) + явный флаг "не брать новые сценарии из scheduler" |
| 9 | Общий риск: сторонние/пользовательские плагины, хранящие "текущий сценарий" в `self.<attr>` между `on_run`/`on_passed`/`on_failed` | Модель событий `Dispatcher` подразумевала строго последовательный поток событий; при параллели события разных сценариев чередуются | Аудит используемых в проекте плагинов перед включением `--parallel`; задокументировать требование реентерабельности обработчиков в README плагина |
| 10 | `artifacted`/`temp_keeper` — работа с директориями артефактов/temp | Потенциальные гонки при одновременной записи/удалении (`shutil.rmtree` и т.п.) | Точечная проверка уникальности путей на сценарий, при необходимости — блокировки на уровне директории |

## 4. Порядок реализации

1. Патчи №1, №3, №4 — блокирующие баги, без них результат некорректен даже на
   простых сценариях без repeat/rerun.
2. Патч №5 (+ проверка №6) — обязателен при совместном использовании с
   `--repeat`/`--reruns`.
3. Патч №2 — обязателен для корректного захвата stdout/stderr в отчёте
   (временный компромисс — отключать `--show-captured-output` при `--parallel`).
4. Патч №8 — обязателен для корректной работы fail-fast.
5. Патч №7 — для юзабельности вывода, не блокирует корректность запуска.
6. Патч №9 — организационный (аудит стороннего кода), не код в vedro.

Патчи №1–4 и №8 реализуемы **без форка ядра vedro**: `OutputCapturer`
подключается через `Registry`-подобные точки/обёртки, а `StepRecorder` и
`Deferrer._queue` — жёстко захардкоженные module-level глобалы (не заведены
как `Factory`/`Singleton` в `core/di`), поэтому патчатся только через
monkey-patch соответствующих модулей на `ConfigLoadedEvent`, до того как
плагины ядра успели забиндиться на глобальные объекты.

## 5. Опциональное развитие: честный GIL-параллелизм

Если чистой asyncio-конкурентности окажется недостаточно (CPU-bound сценарии),
следующий шаг — не subinterpreters (см. отдельный план `02-subinterpreters.md`),
а промежуточный вариант: каждый "слот" параллелизма — отдельный **OS-поток**
со своим `asyncio.run(...)` внутри (по одному сценарию или последовательной
пачке за раз на поток). На GIL-сборках CPython это не даст истинного
параллелизма по CPU, но снимет часть накладных расходов ожидания I/O в разных
потоках одновременно и является более простым шагом, чем subinterpreters.
Настоящее снятие GIL — только на free-threaded CPython 3.13+ (PEP 703),
что требует отдельной валидации всей экосистемы vedro (плагины, C-расширения
зависимостей) на thread-safety.

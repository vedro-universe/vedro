# План: параллельный запуск сценариев через sub-interpreters (PEP 554 / PEP 684)

## Статус
Исследовательский (R&D) план. Существенно более рискованный и трудоёмкий, чем
asyncio-вариант (`01-asyncio-parallel-runner.md`). Рассматривать как решение
для честного использования нескольких ядер CPU **в рамках одного процесса**,
без накладных расходов межпроцессного IPC, характерных для варианта с
обёрткой-оркестратором (`03-multiprocess-wrapper.md`).

## Зачем это нужно, если уже есть asyncio-вариант

asyncio-раннер (план 01) даёт конкурентность, но не параллелизм: все сценарии
делят один GIL и один OS-поток исполнения байткода. Это ускоряет только
I/O-bound нагрузку. Если сценарии CPU-bound (тяжёлые вычисления, сериализация,
крипто, локальный парсинг), нужен реальный параллелизм. Классический ответ —
`multiprocessing`, но это дорого (сериализация состояния, копирование памяти,
холодный старт интерпретатора) и плохо сочетается с моделью Vedro (общий
`Dispatcher`, `Config`, `Report`, плагины — сильно завязаны на общий процесс).

Sub-interpreters — компромисс: несколько изолированных интерпретаторов внутри
одного процесса ОС, каждый с собственным GIL (начиная с PEP 684, CPython 3.12+
даёт per-interpreter GIL), но с более дешёвым, чем процессы, обменом данными
(в перспективе — через `PEP 554`/`interpreters` stdlib модуль, доступный как
публичный API начиная с CPython 3.13 через `concurrent.interpreters`
(ранее — `_xxsubinterpreters` / сторонний backport `interpreters-pep-554`)).

## 1. Принципиальные ограничения, которые определяют дизайн

1. **Изоляция состояния.** Sub-interpreters не разделяют большинство
   Python-объектов "по указателю" — обмен идёт через явные каналы
   (`interpreters.create_channel()`) и сериализуемые/"shareable" типы данных
   (примитивы, `memoryview`, некоторые буферы). Нельзя просто передать
   произвольный Python-объект (например, `Dispatcher`, `Config`, инстансы
   плагинов) между интерпретаторами напрямую.
2. **Каждый интерпретатор — это, по сути, новый процесс Python "изнутри"**:
   свои модули (переимпортируются), свой `sys.modules`, свои глобальные
   синглтоны (в т.ч. все проблемные глобалы из плана 01: `StepRecorder`,
   `Deferrer._queue`, `TempFileManager` и т.д. — но здесь это **не баг, а
   естественная защита**, т.к. у каждого интерпретатора он будет свой).
3. **C-расширения.** Многие C-расширения (в т.ч. используемые транзитивными
   зависимостями пользовательских тестов: `lxml`, `numpy`, драйверы БД и т.п.)
   исторически не поддерживали множественные интерпретаторы в одном процессе
   (общие статические/глобальные C-структуры). PEP 684 требует явной поддержки
   через `Py_mod_multiple_interpreters` слот модуля. Нужно проверять реальный
   стек зависимостей пользовательских проектов — иначе interpreter-worker
   будет падать/крашить процесс целиком при импорте несовместимого расширения.
4. **Event loop asyncio на интерпретатор.** Каждый sub-interpreter должен
   поднимать собственный `asyncio` event loop — кросс-интерпретаторного event
   loop не бывает. Значит, схема аналогична "поток на интерпретатор", просто
   вместо потока — интерпретатор с собственным GIL.
5. **Vedro-объекты не шарятся между интерпретаторами.** `Dispatcher`,
   `ConfigType`, `Plugin`-инстансы, `ScenarioScheduler` — все должны быть
   созданы заново внутри каждого sub-interpreter. Общим может быть только:
   список путей/имён сценариев для исполнения (сериализуемые строки) и
   финальный сериализованный результат (`ScenarioResult`/`AggregatedResult`
   в виде dict/JSON, а не "живые" Python-объекты со ссылками на функции/классы
   тестового кода).

## 2. Архитектура

### 2.1 Оркестрация на уровне процесса

`InterpreterParallelRunner(ScenarioRunner)`:
1. Получает от `scheduler` полный список сценариев (аналогично `Slicer` —
   но не через межпроцессный флаг, а внутри одного `run()`).
2. Делит список на `K` "под-партий" (`K` = число worker-интерпретаторов,
   аналог `--parallel`), используя ту же стратегию, что и
   `SkipAdjustedSlicingStrategy` (переиспользовать код `vedro.plugins.slicer`).
3. Для каждой партии создаёт sub-interpreter (`interpreters.create()`),
   запускает в нём "мини-раннер" (упрощённая копия `RunCommand` без CLI-слоя):
   заново собирает `Config`/`Dispatcher`/плагины (только необходимый набор —
   как минимум те, что влияют на исполнение и репортинг конкретного
   сценария), крутит `MonotonicScenarioRunner` **внутри интерпретатора**,
   сериализует получившиеся `ScenarioResult` в примитивный формат (dict/JSON)
   и кладёт в межинтерпретаторный канал (`interpreters.create_channel()`).
4. Главный интерпретатор читает результаты из каналов по мере готовности,
   десериализует их обратно в `ScenarioResult`/`AggregatedResult` объекты
   (потребуется восстановить ссылку на исходный `VirtualScenario` по
   `unique_id` — он у главного интерпретатора уже есть из `discovered`),
   и подаёт в `Report`/`Dispatcher` главного процесса — чтобы репортеры
   (Rich/JSON/PyCharm) видели единый поток событий, как будто всё выполнялось
   монотонно.

### 2.2 Что переиспользуется без изменений

- `MonotonicScenarioRunner` — как есть, работает внутри каждого
  sub-interpreter изолированно (никакой конкурентности внутри партии не
  нужно, партия исполняется последовательно её собственным раннером).
- Стратегия среза сценариев — код `vedro.plugins.slicer._slicing_strategy`.
- Формат `ScenarioResult`/`StepResult` — при условии, что будет добавлен
  (де)сериализатор в примитивные структуры (см. раздел 3, пункт 3).

### 2.3 Что нужно построить с нуля

- Прокладка "мини-раннер в интерпретаторе" — упрощённый аналог
  `RunCommand.run()`, работающий без argv/CLI, принимающий уже готовый
  `Config` (точнее — путь к нему, чтобы конфиг был переимпортирован заново
  внутри интерпретатора, т.к. живые объекты Config через границу не передать).
- Транспортный слой result-passing через `interpreters.create_channel()`
  (или через `multiprocessing.shared_memory`-подобные буферы, если
  канал-API окажется неудобным для сложных вложенных структур).
- "Прокси-репортинг": события `ScenarioRunEvent`/`StepPassedEvent`/... либо
  (а)完全 не долетают до главного интерпретатора в реальном времени, и
  репорт строится только по завершении партии целиком (проще, но теряется
  живой прогресс-бар), либо (б) нужен стриминг лёгких "тиков" через канал
  ("scenario X started/passed/failed") — сложнее, но сохраняет live-UX.

## 3. Список мест для доработки/патча

| № | Область | Проблема | Что делать |
|---|---|---|---|
| 1 | Доступность API | `interpreters`/`concurrent.interpreters` — публичный stdlib API только с CPython 3.13+; на более старых версиях нужен backport-пакет (`interpreters-pep-554`) или приватный `_xxsubinterpreters` (нестабильный, недокументированный) | Зафиксировать минимальную поддерживаемую версию Python для этого режима (рекомендация: жёстко требовать 3.13+, деградация в план 01/03 на более старых) |
| 2 | Совместимость C-расширений тестового проекта | Модули без `Py_mod_multiple_interpreters` не грузятся в sub-interpreter (или ведут себя непредсказуемо) | На старте worker-интерпретатора — попытка импорта всех модулей, используемых сценариями; при ошибке — понятная диагностика ("модуль X не поддерживает sub-interpreters, используйте --parallel-mode=process") |
| 3 | (Де)сериализация `ScenarioResult`/`StepResult`/`ExcInfo`/`Artifact` | Эти объекты сейчас содержат живые ссылки на функции, классы сценариев, traceback-объекты, файловые артефакты — не являются "shareable" между интерпретаторами | Добавить сериализатор в примитивы (dict/JSON-совместимый) + десериализатор на стороне главного интерпретатора, который восстанавливает связь с исходным `VirtualScenario` по `unique_id` из `scheduler.discovered` |
| 4 | Все глобальные синглтоны плагинов (`StepRecorder`, `Deferrer._queue`, `TempFileManager`, `ArtifactManager`) | Здесь это не баг (у каждого интерпретатора свой), НО: они инициализируются как module-level переменные при импорте — нужно убедиться, что переимпорт модуля в новом интерпретаторе действительно создаёт новый инстанс, а не переиспользует что-то через C-уровень кэширования модулей | Ревизия: явно тестировать под sub-interpreters каждый плагин ядра |
| 5 | `Dispatcher`/`Config`/DI-контейнеры (`core/di`) | Не спроектированы для пересоздания "по требованию" в изолированном контексте — сейчас это фактически singleton на процесс (`FrozenSingleton` для Dispatcher) | Нужна отдельная точка входа "создать полный стек Vedro внутри текущего интерпретатора с нуля", которой сейчас нет как переиспользуемой функции — придётся выделить из `RunCommand` |
| 6 | Файловая система / `os.chdir`, temp-директории, артефакты | При параллельном исполнении партий в разных интерпретаторах (но одном процессе, значит один и тот же `cwd` ОС!) — проблема `os.chdir` из плана 01 актуальна и здесь, и без общего GIL для сериализации доступа к `cwd` она хуже, а не лучше | Обязательно убрать per-scenario `chdir` (см. план 01, патч №1) — здесь это блокер, а не опциональная доработка |
| 7 | Отчётность/live-вывод | Нет единого потока событий в реальном времени между интерпретаторами "из коробки" | См. 2.3 — либо батчевый репорт по завершении партии, либо лёгкий event-streaming через канал |
| 8 | Отладка и стабильность | Sub-interpreters в CPython всё ещё считаются developing-фичей: возможны падения интерпретатора, memory leaks при частом create/destroy, слабая экосистема отладочных инструментов (pdb/трейсинг может не работать штатно между интерпретаторами) | Заложить в план explicit fallback на процессный вариант (план 03) при сбое инициализации интерпретатора; не использовать в production без длительного пилота |

## 4. Оценка целесообразности

Учитывая объём необходимой инфраструктуры (пп. 2.1–2.3 и патчи 3, 5, 7) и
незрелость экосистемы (п. 8), этот вариант имеет смысл начинать только после
того, как:
- вариант 01 (asyncio) внедрён и упирается в CPU, а не I/O;
- вариант 03 (обёртка/несколько процессов) признан недостаточным по накладным
  расходам (холодный старт процесса, сериализация всего конфига, отсутствие
  общего логирования/прогресс-бара).

Рекомендация: держать этот план как R&D-трек с низким приоритетом, не
начинать реализацию до валидации гипотезы "тесты действительно CPU-bound"
на конкретных проектах пользователей Vedro.

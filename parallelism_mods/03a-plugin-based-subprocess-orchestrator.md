# Дополнение к плану 03: оркестрация подпроцессов из плагина (без внешнего скрипта-обёртки)

Этот документ детализирует вариант 03 (`03-multiprocess-wrapper.md`), заменяя
"внешний CLI-скрипт над vedro" на **плагин Vedro**, который сам является
`ScenarioRunner` и сам оркеструет подпроцессы, интегрируя результат обратно
в родной pipeline событий/отчётности основного процесса. Отвечает на вопрос:
"можно ли слияние сделать плагином, который инициирует запуск и возвращает
структуры данных в основной процесс, не нарушая структуру результатов".

**Короткий ответ: да, можно, и это архитектурно чище, чем отдельный скрипт.**
Все технические предпосылки для этого уже есть в ядре:
- `Registry.ScenarioRunner.register(...)` — штатная точка подмены раннера
  (используется `DryRunnerPlugin`, см. `01-asyncio-parallel-runner.md`, раздел 1).
- `Dispatcher.fire(...)` — можно вызывать вручную из кастомного раннера с
  любыми валидными событиями, репортеры на это никак не завязаны на "кто
  вызвал fire" — они просто подписчики.
- JSON-протокол уже существует (`JsonReporter`, NDJSON-события в stdout) —
  готовый (почти) формат для передачи структурированных результатов из
  дочернего процесса в родительский.

## 1. Общая идея

Вместо внешнего скрипта — один плагин `ParallelOrchestrator`
(`PluginConfig` + `Plugin`), который:

1. На `ArgParsedEvent`/`ConfigLoadedEvent` включается по флагу `--workers N`
   (N > 1) и на этом же шаге регистрирует себя как `ScenarioRunner`:
   `Registry.ScenarioRunner.register(resolver=lambda: SubprocessOrchestratorRunner(...), registrant=self)`.
2. При вызове `run(scheduler, **kwargs)` (это и есть штатный вход раннера,
   вызываемый `RunCommand` вместо `MonotonicScenarioRunner.run`):
   - забирает список сценариев из `scheduler.discovered` (уже открыт и
     упорядочен основным процессом — переиспользуем один discovery, а не
     дублируем его в каждом подпроцессе, в отличие от плана 03 "как есть",
     где `Slicer` внутри дочернего `vedro run` делает discovery заново);
   - делит список на N партий (переиспользуя стратегию
     `vedro.plugins.slicer._slicing_strategy.SkipAdjustedSlicingStrategy`
     или свою — важно: не полагаться на повторный запуск `Slicer` в
     дочернем процессе, а явно передать каждому дочернему процессу точный
     список путей файлов сценариев, чтобы результат партиционирования не
     зависел от независимого re-discovery в двух местах);
   - запускает N подпроцессов `vedro run <файлы партии i> <passthrough
     аргументы> --reporter <internal-ndjson>` через `asyncio.create_subprocess_exec`
     (не `subprocess.Popen` — раннер асинхронный, удобнее нативно ждать
     несколько процессов конкурентно через `asyncio.gather`/`TaskGroup`);
   - **не ждёт** тупо завершения всех, а построчно читает stdout каждого
     подпроцесса по мере поступления (NDJSON — одна строка = одно событие),
     сразу конвертирует событие в объекты ядра (`ScenarioResult`/`StepResult`)
     и **файрит эквивалентные события в `Dispatcher` основного процесса** —
     это даёт live-прогресс "бесплатно": родной `RichReporter` в основном
     процессе видит `ScenarioRunEvent`/`ScenarioPassedEvent` как будто сам
     их сгенерировал.
   - по завершении всех подпроцессов возвращает единый `Report` (как и
     положено интерфейсу `ScenarioRunner.run()`), собранный из
     `scheduler.aggregate_results(...)` для каждого `unique_id` — точно так
     же, как это делает `MonotonicScenarioRunner._report_scenario_results`.

## 2. Почему это не ломает структуру результатов (ключевой момент вопроса)

Момент, который стоит подчеркнуть отдельно: проблема "параллельного
чередования событий", описанная в плане 01 (пункт 7 таблицы — репортеры
рассчитаны на один активный сценарий в моменте), **здесь не возникает**,
хотя реальное исполнение и происходит параллельно (в разных процессах).

Причина: каждый дочерний процесс сам исполняет свою партию сценариев
**последовательно** (обычным `MonotonicScenarioRunner` внутри), значит его
NDJSON-поток — это корректный, полностью последовательный, "правильно
вложенный" поток событий одного сценария за другим (Run → Step* → Passed/Failed
→ Reported), без какого-либо смешивания. Родительский процесс читает N таких
потоков конкурентно (по мере готовности данных), но может решить, **как**
их сшивать в единый Dispatcher основного процесса:

- **Вариант А (проще, рекомендуется по умолчанию):** ретранслировать события
  "как есть", по мере поступления от любого воркера — тогда в основном
  процессе события *разных* сценариев формально чередуются во времени (ровно
  как физически и происходило), но при этом единый сценарий внутри себя
  остаётся целостной, неразрывной последовательностью (Run→Step→Reported для
  сценария X никогда не прерывается событием сценария Y "посередине" —
  события приходят из одного NDJSON-потока строка за строкой). Это уже
  снимает ключевой риск из плана 01: там был риск, что **сам захват
  вывода/степов одного сценария** физически перемешивается с другим
  (общий `sys.stdout`, общий `StepRecorder`) — здесь такого нет, каждый
  сценарий целиком считан и обработан как атомарный блок событий одного
  воркера.
- **Вариант Б (для максимально "красивого" вывода):** буферизовать полностью
  завершённые сценарии (ждать `ScenarioReportedEvent` для сценария X) и
  файрить пачку его событий в основной `Dispatcher` только целиком и без
  прерываний другим воркером между ними (простая блокировка/очередь на
  "фазу выдачи"), жертвуя малой долей live-эффекта ради полностью
  детерминированного, "не чередующегося" вывода в консоли — практически
  то же поведение, что видит пользователь `pytest -n auto` с построчной
  агрегацией по воркеру.

Рекомендация: реализовать вариант А как MVP (проще, событийная модель и так
устойчива к чередованию *между* разными сценариями — плагины ядра, в
отличие от кейса "конкурентность внутри одного процесса", не хранят
per-scenario состояние совместно между двумя *разными* сценариями), вариант
Б — как флаг `--parallel-output=grouped` для тех, кому важен красивый терминал.

## 3. Как выглядит "не нарушая структуру результатов"

Формально `ScenarioResult`/`StepResult`/`AggregatedResult` в основном
процессе — это **новые объекты**, создаваемые заново на основе данных из
NDJSON, а не "пересланные" объекты дочернего процесса (Python-объекты со
ссылками на функции/traceback нельзя передать через границу процесса как
есть — только сериализуемые данные). Но структура результата (граф
"сценарий → шаги → статус/тайминги/артефакты") воссоздаётся один в один:

1. `VirtualScenario` для конкретного `unique_id` **уже есть** в основном
   процессе (это тот же объект из `scheduler.discovered`, который получил
   этот же `unique_id` при discovery в родителе) — его пересобирать не
   нужно, только найти по `unique_id` в уже известном словаре.
2. На основе него создаётся новый `ScenarioResult(scenario)`, в который
   построчно (из NDJSON) переносятся: статус, `started_at`/`ended_at`,
   список `StepResult` (имя шага, статус, тайминг), `captured_output` (если
   включён показ вывода — текст стдаут/стдерр как обычные строки, без
   проблемы "общего sys.stdout", т.к. каждый воркер захватывал свой вывод
   в изоляции ОС-процесса), `extra_details`.
3. Для агрегации (`--repeat`/`--reruns` внутри партии) — воркер сам считает
   агрегацию локально через свой `scheduler.aggregate_results(...)` и
   присылает уже готовый `AggregatedResult`; либо, если `--reruns`
   назначается на уровне партии, а не сценария, родитель может достроить
   финальную агрегацию сам, зная, что все повторы конкретного `unique_id`
   гарантированно попали в один и тот же воркер (это нужно явно
   гарантировать в логике партиционирования — не разбивать копии одного и
   того же сценария по разным воркерам).

## 4. Ограничение, которое нужно явно задокументировать: исключения/traceback

`ExcInfo` в ядре — это тройка `(exc_type, exc_value, traceback)`, требуемая
многими механизмами (`TracebackFilter`, форматирование traceback в
`RichReporter`). Через границу процесса нельзя передать "живой"
traceback-объект (он не сериализуется). Уже существующий `JsonReporter`
решает эту проблему тем же способом, каким придётся решать и здесь:
передавать не сам traceback, а его **текстовое представление** плюс сводку
(`type`, `message`, `file`, `lineno`) — см. `ExcInfoDict` в
`vedro/plugins/director/json/_event_types.py`. Соответственно, в основном
процессе на основе такого dict создаётся **синтетический** объект-обёртка
(например, собственное исключение с восстановленным текстом traceback как
атрибутом/сообщением), а не оригинальный `ExcInfo` с реальными фреймами.

Практическое следствие: репортеры, которые рисуют traceback **как отформатированный
текст** (обычный путь показа ошибки пользователю) — будут работать
корректно. Инструменты/плагины, которые пытаются программно анализировать
реальные фреймы traceback (интроспекция стека, кастомные дебаггеры) —
работать не будут, т.к. фреймов физически нет. Это нужно явно указать в
документации плагина как принципиальное ограничение подхода (одинаково
актуальное что для этого плагина, что для "плана 03 как есть" с JSON-мерджем).

## 5. Отличия от "плана 03 как есть" (внешний скрипт)

| Аспект | 03 (внешний скрипт) | 03 + плагин-оркестратор (этот документ) |
|---|---|---|
| Точка запуска | Отдельная CLI-утилита поверх `vedro` | Сам `vedro run --workers N` — ничего дополнительного ставить не нужно |
| Discovery сценариев | Дублируется в каждом дочернем `vedro run` (свой `Slicer`) | Выполняется один раз в родителе, дочерним процессам передаётся уже готовый список файлов |
| Формирование финального отчёта | Отдельный мерж-скрипт вне vedro, свой формат вывода | Родной `Report`/`Dispatcher` основного процесса — работают все штатные репортеры (Rich/Json/PyCharm) без доработок под "мердж" |
| Live-вывод | Требует ручной ретрансляции stdout дочерних процессов с префиксами | Получается "естественно" через фактическую ретрансляцию событий в `Dispatcher` (раздел 2) |
| Точка расширения в vedro | Не нужна вообще (чистый внешний слой) | Нужна одна и та же официальная точка — `Registry.ScenarioRunner.register(...)` (как у `DryRunner`) |
| Риск версийной деприкации | Отсутствует (это внешний код, не завязан на internal API раннера) | Присутствует (тот же нюанс, что и у плана 01 — `Registry.ScenarioRunner` помечен как "не для кастомных раннеров", будет меняться в v2) |
| Сложность реализации | Проще (шелл-скрипт/питон-скрипт + json.load + print) | Чуть сложнее (нужен NDJSON-протокол потребления событий "на лету" + реконструкция объектов результатов), но даёт качественно лучший UX "из коробки" |

## 6. Итоговые технические компоненты плагина (без кода, только состав)

1. `ParallelOrchestrator` (`PluginConfig`) — CLI: `--workers N`,
   `--parallel-output=live|grouped` (см. раздел 2), скрытый флаг/переменная
   окружения для дочерних процессов (`VEDRO_PARALLEL_WORKER=1`), чтобы
   дочерний `vedro run` гарантированно не пытался сам заново
   развернуть N воркеров (защита от рекурсии).
2. `SubprocessOrchestratorRunner(ScenarioRunner)` — основная логика:
   партиционирование, `asyncio.create_subprocess_exec`, построчное чтение
   `stdout` каждого подпроцесса, диспетчеризация в `Dispatcher` родителя.
3. Внутренний "машинный" репортер для дочерних процессов — либо
   переиспользуется существующий `JsonReporter` "как есть" (минимизирует
   код, но привязывает к его текущей схеме `EventDict`/`ScenarioDict`/
   `StepDict`, которая может измениться в будущих версиях vedro и не
   специфицирована как стабильный публичный контракт), либо заводится
   собственный приватный NDJSON-формат, специально для передачи
   данных между процессами одного и того же плагина (более устойчиво к
   будущим изменениям `JsonReporter`, но требует написать свой
   форматтер вместо переиспользования существующего).
   **Рекомендация:** начать с переиспользования `JsonReporter` для скорости
   MVP, заложить абстракцию (интерфейс "результат-парсер"), чтобы можно
   было безболезненно перейти на собственный формат, если схема
   `JsonReporter` в новой версии vedro перестанет устраивать.
4. Реконструктор результатов — сопоставление `unique_id` из NDJSON с
   `VirtualScenario` из `scheduler.discovered` основного процесса + сборка
   `ScenarioResult`/`StepResult`/`AggregatedResult`/синтетического `ExcInfo`
   (раздел 3–4).
5. Пробрасыватель CLI-аргументов (passthrough) — сбор исходных
   аргументов запуска (кроме `--workers`/служебных флагов плагина) для
   передачи в каждый дочерний `vedro run`.
6. Обработка сигналов/`--fail-fast` — при получении `SIGINT` или срабатывании
   `Interrupter` в родительском процессе (сам `Interrupter` слушает и в
   основном процессе тоже, если сконфигурирован) — рассылка `SIGTERM` во
   все ещё работающие дочерние процессы, ожидание грациозного завершения с
   таймаутом.
7. Изоляция побочных ресурсов дочерних процессов — как и в "плане 03 как
   есть", каждому воркеру передаётся свой `--tmp-dir` и (если нужно) свой
   путь артефактов, чтобы избежать гонок в `TempKeeper`/`ArtifactManager`.

## 7. Резюме

Да, реализация в виде плагина, который сам инициирует запуск дочерних
`vedro run` и возвращает структуры результатов в основной процесс —
не только возможна, но и **предпочтительнее** "чистого варианта 03"
(внешнего скрипта), потому что:
- переиспользует единый discovery вместо его дублирования;
- отдаёт финальный отчёт через штатный `Report`/`Dispatcher`, а не через
  отдельный мердж-скрипт вне vedro — все существующие репортеры работают
  без доработок;
- даёт live-прогресс "естественным" образом, без обхода через ретрансляцию
  сырого stdout с префиксами;
- не сталкивается с проблемой "разорванных" по времени, перемешанных
  событий одного сценария, потому что каждый дочерний процесс сам
  гарантирует целостный, последовательный поток событий для своей партии.

Цена за это — на одну точку зависимости от internal API больше
(`Registry.ScenarioRunner`, помеченный deprecated-в-сторону-v2), и заметно
больше кода, чем "просто скрипт + json.load" из исходного плана 03.
Рекомендуется как **основной путь реализации плана 03** при наличии
ресурсов на его разработку; чистый внешний скрипт — как временный/самый
быстрый MVP, если нужен результат "уже сегодня, минимальными усилиями".

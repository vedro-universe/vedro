# План: параллельный запуск через обёртку — несколько процессов `vedro run` + склейка отчётов

## Статус
Наиболее простой и низкорисковый вариант. Не требует изменений в самом
`vedro` вообще (кроме, возможно, небольшого доп. режима вывода отчёта в файл,
если такого ещё нет) — почти всё уже есть в ядре (`Slicer`), не хватает только
внешнего скрипта-оркестратора и шага слияния (merge) отчётов.

## Идея

Запустить N параллельных ОС-процессов `vedro run`, каждый — со своим
непересекающимся подмножеством сценариев (через уже существующий
`--slice <i>/<N>` из плагина `Slicer`, либо через `--slicer-index`/`--slicer-total`),
дождаться завершения всех, собрать их машиночитаемые отчёты (`JsonReporter`) и
склеить в один итоговый отчёт/exit-code для CI.

Это даёт честный параллелизм по CPU (реальные ОС-процессы, полная изоляция
GIL, состояния плагинов, файловой системы — если развести temp/artifacts
директории), ценой более дорогого старта (каждый процесс поднимает свой
интерпретатор, заново импортирует конфиг и тестовые модули) и отсутствия
единого live-вывода без дополнительной работы.

## 1. Что уже есть в ядре и переиспользуется как есть

- `vedro/plugins/slicer/_slicer.py` — уже умеет делить `discovered`-сценарии
  на `N` непересекающихся частей через `--slice <index>/<total>`
  (1-based) или `--slicer-index`/`--slicer-total` (0-based, legacy). Никаких
  правок не требуется — это и есть механизм разбиения набора тестов на потоки.
- `vedro/plugins/director/json/_json_reporter.py` — уже даёт машиночитаемый
  JSON-отчёт (`--reporter json`), пригодный для последующего программного
  слияния (нужно только проверить, что схема отчёта достаточно полна для
  склейки: список сценариев, статусы, тайминги, summary/статистика).

## 2. Что нужно построить (сама обёртка)

Отдельный CLI-инструмент/скрипт (`vedro-parallel` или Makefile-таргет),
не являющийся плагином vedro, а внешним оркестратором:

1. **Определение количества воркеров** — вход: `--workers N` (или
   `os.cpu_count()` по умолчанию).
2. **Опциональная предварительная балансировка** — по умолчанию `Slicer`
   делит по индексу с равномерным round-robin (см.
   `SkipAdjustedSlicingStrategy`), что не учитывает разное время выполнения
   разных сценариев. Для более честного баланса — использовать историю
   времени выполнения прошлых прогонов (если у vedro есть подобный
   отчёт/лог с таймингами на сценарий — использовать его как веса и сделать
   собственный "smart split", передавая уже готовые списки путей файлов
   сценариев через существующие позиционные аргументы `vedro run <path...>`
   вместо `--slice`, если понадобится покастомнее балансировать, чем
   round-robin).
3. **Запуск N процессов** `vedro run --slice i/N --reporter json
   --json-report-path ./.reports/report-{i}.json <общие CLI-аргументы>`
   через `subprocess.Popen`, параллельно, с ожиданием всех (`asyncio.gather`
   на уровне обёртки или `concurrent.futures.ProcessPoolExecutor`/
   `multiprocessing.Pool` — обёртка сама может быть однопоточным скриптом,
   которому не важна модель ядра vedro).
4. **Изоляция побочных ресурсов между воркерами** — каждому процессу
   передать свой `--tmp-dir`/рабочую под-директорию для артефактов
   (`--tmp-dir .vedro/tmp/worker-{i}`), чтобы не было гонок в
   `TempKeeper`/`ArtifactManager` (см. раздел 3, пункт 2).
5. **Сбор кодов возврата** — итоговый exit code обёртки = `0`, если у всех
   процессов `0`, иначе ненулевой (аналогично поведению `pytest-xdist`).
6. **Merge отчётов** — отдельный шаг, читающий `report-{i}.json` от всех
   воркеров и производящий:
   - объединённый список результатов сценариев (конкатенация, т.к. наборы
     не пересекаются по построению `Slicer`);
   - пересчитанную агрегированную статистику (`passed/failed/skipped/total`,
     суммарное время — как сумма или как `max` по воркерам в зависимости от
     того, что нужно показывать: "человеко-время" или "wall-time прогона");
   - единый итоговый JSON/консольный вывод (переиспользовать форматирование
     `RichReporter`, но не как vedro-плагин, а как отдельный
     скрипт-презентер поверх объединённых данных — либо просто печатать
     сводную таблицу без стилизации Rich, чтобы не тащить зависимость).
7. **(Опционально) Живой прогресс** — пока воркеры работают, можно
   параллельно "хвостить" их stdout (`Popen(..., stdout=PIPE)`) и построчно
   ретранслировать в объединённый терминал с префиксом `[worker i]`, чтобы
   не терять фидбек в реальном времени (простое и надёжное решение, в
   отличие от вариантов 01/02, где на живой вывод нужны отдельные патчи
   репортера).

## 3. Список мест для доработки/проверки

| № | Область | Проблема | Что делать |
|---|---|---|---|
| 1 | Полнота `JsonReporter` | Нужно убедиться, что JSON-отчёт содержит достаточно данных для честного merge: причины падений, шаги, тайминги, summary-метрики, а не только "прошёл/не прошёл" | Изучить `vedro/plugins/director/json/_json_reporter.py` — при необходимости расширить набор полей (это уже точечная правка в самом vedro, т.к. `JsonReporter` — часть ядра, а не сторонний плагин) |
| 2 | `TempKeeper`/`ArtifactManager` — общая `.vedro/tmp/`, `.vedro/artifacts/` директория по умолчанию | При параллельных процессах, если явно не развести пути, возможны гонки при `shutil.rmtree`/записи файлов между воркерами | Обёртка обязана передавать каждому процессу собственный `--tmp-dir` (и, если появится — аналогичный флаг для artifacts, сейчас нужно проверить, есть ли отдельный CLI-флаг для `artifacts_dir` у `ArtifactManager`/`Artifacted`-плагина, иначе — сделать общий, но с уникальным префиксом на воркера через `PROJECT_DIR`/окружение) |
| 3 | Стратегия балансировки `Slicer` (`SkipAdjustedSlicingStrategy`) | Round-robin по индексу без учёта времени выполнения — при неравномерных по длительности сценариях воркеры финишируют не одновременно (простаивание) | Не патч ядра, а доработка на уровне обёртки: собственная стратегия распределения (custom `BaseSlicingStrategy`, доступный как параметр `Slicer.slicing_strategy` в конфиге проекта) на основе исторических таймингов, либо просто явная передача заранее вычисленных списков файлов сценариев в каждый процесс вместо `--slice` |
| 4 | Общие ресурсы вне vedro (внешние сервисы, БД, порты, фикстуры окружения) | Это уже не про сам vedro, а про тестовые сценарии пользователя — при физическом параллелизме процессов конфликты по общим портам/БД/сидированным данным становятся реальны (в отличие от строго последовательного запуска) | Не патч vedro — организационная рекомендация в документации: тестовые сценарии, рассчитанные на параллельный запуск, не должны разделять мутируемое внешнее состояние (аналогично требованиям pytest-xdist к тестам) |
| 5 | Порядок/детерминированность отчёта | Конкатенация результатов от разных воркеров даст произвольный (по завершению) порядок сценариев в объединённом отчёте вместо порядка обнаружения | Мердж-скрипту сортировать результат по исходному индексу обнаружения (нужно, чтобы `Slicer`/обёртка сохраняли исходный порядковый номер сценария вместе с результатом — уже есть `unique_id`, порядок discovery можно восстановить, отсортировав по нему на этапе подготовки списков для воркеров) |
| 6 | Exit-code и сигналы (Ctrl+C) | Нужно корректно прокидывать `SIGINT`/`SIGTERM` во все дочерние процессы и дожидаться их грациозного останова (у ядра уже есть `InterrupterPlugin`, реагирующий на сигналы внутри одного процесса — но координация "остановить все N процессов разом" — забота обёртки) | В обёртке — перехват сигнала в родительском процессе, рассылка сигнала во все `Popen`-дочерние, ожидание с таймаутом, затем `kill -9` при необходимости |
| 7 | CLI-совместимость произвольных пользовательских аргументов | Обёртка должна прозрачно прокидывать все остальные флаги `vedro run` (`--tags`, `--reruns`, кастомные плагины и т.д.) в каждый под-процесс без потери | Реализовать как "passthrough" всех аргументов, кроме зарезервированных обёрткой (`--workers`, возможно `--slice`, которые обёртка выставляет сама) |

## 4. Плюсы и минусы относительно вариантов 01/02

Плюсы:
- Не требует патчей ядра/плагинов вообще (все проблемы из планов 01 и 02 —
  `os.chdir`, `StepRecorder`, `Deferrer._queue`, `OutputCapturer` — здесь
  **не актуальны**, т.к. каждый процесс полностью изолирован ОС).
- Честный параллелизм по CPU уже сегодня, на любой версии Python.
- `Slicer` для разбиения — уже существующий, протестированный код.

Минусы:
- Накладные расходы на старт процесса (импорт конфигурации/тестовых модулей
  N раз) — заметно на маленьких сценариях/маленьких сьютах.
- Нет единого live-отчёта "из коробки" — либо ждать все воркеры до конца,
  либо реализовывать построчную ретрансляцию stdout (раздел 2, пункт 7).
- Балансировка нагрузки грубая (round-robin), требует доп. работы для
  честного распределения по времени выполнения.
- Итоговый отчёт — результат постобработки внешним скриптом, а не
  "нативный" вывод vedro — риск расхождений в форматировании/метриках,
  если `JsonReporter` в будущих версиях vedro поменяет схему без учёта
  внешнего мерж-скрипта (нужно версионировать схему и покрыть тестами сам
  merge-скрипт).

## 5. Рекомендация

Это самый быстрый в реализации и самый безопасный по рискам вариант —
рекомендуется как **первый шаг** ("уже работает почти из коробки"), пока
вариант 01 (asyncio-раннер) дорабатывается и проходит через список патчей
совместимости. Вариант 02 (sub-interpreters) — держать в бэклоге как R&D.

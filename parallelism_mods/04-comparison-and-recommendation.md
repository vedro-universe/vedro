# Сравнение вариантов параллелизации Vedro и рекомендация

Сравниваются три плана:
- **01 — asyncio-раннер** (`01-asyncio-parallel-runner.md`)
- **02 — sub-interpreters** (`02-subinterpreters-runner.md`)
- **03 — обёртка над несколькими процессами `vedro run`** (`03-multiprocess-wrapper.md`)

## 1. Критерии сравнения

| Критерий | Почему важен |
|---|---|
| Честный параллелизм по CPU | Даёт ли вариант реальное ускорение на CPU-bound сценариях, а не только на I/O-ожиданиях |
| Изоляция состояния (GIL/глобалы/файлы) | Насколько сильно вариант подвержен проблемам общих глобалов (`StepRecorder`, `Deferrer`, `os.chdir`, `OutputCapturer` и т.п.), описанным в планах 01/02 |
| Объём патчей в самом vedro | Сколько мест в ядре/плагинах нужно патчить или обходить monkey-patch'ем |
| Совместимость с текущим API/версией Python | Работает ли на текущей ветке 1.x без спец. версии интерпретатора |
| Готовность экосистемы / зрелость технологии | Насколько технология стабильна и документирована в CPython/сообществе |
| Сложность реализации (трудозатраты) | Условная оценка объёма работ до рабочего MVP |
| Риск для продакшена | Вероятность падений/некорректных результатов/трудноуловимых багов |
| Накладные расходы (overhead) | Потери на старт, сериализацию, межпроцессный/межинтерпретаторный обмен |
| Live-отчётность / UX вывода | Насколько просто сохранить читаемый прогресс выполнения в реальном времени |
| Совместимость со `Slicer` (межмашинный параллелизм) | Можно ли комбинировать с уже существующим межпроцессным/межмашинным разбиением |
| Влияние на сторонние плагины пользователей | Насколько вероятно, что плагины проекта (не из ядра) сломаются "молча" |

## 2. Таблица сравнения

| Критерий | 01. asyncio-раннер | 02. sub-interpreters | 03. обёртка (multi-process) |
|---|---|---|---|
| Честный параллелизм по CPU | ❌ Нет (один GIL/поток, только конкурентность на I/O) | ✅ Да (per-interpreter GIL, PEP 684) | ✅ Да (реальные ОС-процессы) |
| Изоляция состояния | ⚠️ Низкая — требует ручного патча всех глобалов (пп. 1–4 плана 01) | ✅ Высокая "по построению" (глобалы автоматически разделены по интерпретаторам), но требует ручной сериализации результатов | ✅ Максимальная — полная изоляция ОС-процессом, патчи ядра не нужны |
| Объём патчей в vedro | 🔴 Много (10 пунктов, 5 из них блокирующие: chdir, StepRecorder, Deferrer, группировка результатов, Interrupter) | 🔴🔴 Ещё больше + инфраструктура с нуля (сериализация ScenarioResult, прокладка "мини-раннер в интерпретаторе", event-streaming) | 🟢 Практически ноль (максимум — расширение полноты `JsonReporter`) |
| Совместимость с Python 1.x/текущей версией | ✅ Работает уже сейчас (3.8+) | 🔴 Требует CPython 3.13+ (публичный API) или нестабильный backport/приватный `_xxsubinterpreters` | ✅ Работает уже сейчас, без ограничений по версии |
| Зрелость технологии | ✅ asyncio — давно стабилен | 🔴 Sub-interpreters — экспериментальная, малодокументированная область (риск падений, слабый tooling для отладки) | ✅ `subprocess`/`multiprocessing` — максимально зрелые |
| Сложность реализации | 🟡 Средняя | 🔴 Высокая | 🟢 Низкая |
| Риск для продакшена | 🟡 Средний (много точечных патчей = риск регрессий, но локализованы) | 🔴 Высокий (незрелая технология + риск несовместимости C-расширений пользовательских тестов) | 🟢 Низкий (изоляция процессом убирает целый класс багов) |
| Overhead | ✅ Минимальный (один процесс, общая память) | 🟡 Средний (создание интерпретатора дешевле процесса, но дороже task'а; сериализация на границах) | 🔴 Наибольший (N полных запусков интерпретатора, повторный импорт конфига/тестов) |
| Live-отчётность / UX | 🟡 Нужен отдельный parallel-aware репортер (буферизация вывода на сценарий) | 🔴 Сложнее всего — нет встроенного стриминга между интерпретаторами, нужен свой протокол "тиков" | 🟢 Просто — построчная ретрансляция stdout дочерних процессов с префиксом воркера |
| Совместимость со `Slicer` | ✅ Полностью (Slicer работает на уровне scheduler до создания раннера) | ✅ Совместимо (внутри одного процесса можно применить тот же принцип среза) | ✅ Является прямым продолжением/использованием `Slicer` |
| Риск для сторонних плагинов пользователей | 🔴 Высокий — любой плагин, хранящий "текущий сценарий" в `self.attr`, тихо ломается (п. 9 плана 01) | 🔴 Высокий — плюс риск несовместимости C-расширений тестового стека (п. 2 плана 02) | 🟢 Минимальный — плагины продолжают работать как в обычном последовательном прогоне, каждый в своём процессе |

Легенда: ✅ хорошо / 🟢 низкий риск или простота / 🟡 средне / 🔴 плохо, высокий риск или сложность.

## 3. Взвешенный итог

Если считать по количеству "🔴" (существенные минусы):
- **01 (asyncio)** — 2 красных (глубина патчей, риск для сторонних плагинов), но всё остальное умеренно или хорошо.
- **02 (sub-interpreters)** — 6 красных практически по всем ключевым критериям: версия Python, зрелость, сложность, риск, UX, сторонние плагины.
- **03 (обёртка)** — 1 красный (overhead запуска), остальное зелёное/приемлемое.

## 4. Рекомендация

**Выбор: вариант 03 — обёртка над несколькими процессами `vedro run` + слияние JSON-отчётов.**

Обоснование:
- Даёт **настоящий** параллелизм по CPU уже сегодня, без ожидания зрелости sub-interpreters и без версионных ограничений.
- Требует **нулевых или минимальных изменений в самом vedro** — все проблемы глобального состояния (`os.chdir`, `StepRecorder`, `Deferrer._queue`, `OutputCapturer`), которые являются центральной болью планов 01 и 02, здесь просто не существуют благодаря изоляции ОС-процессом.
- Наименьший риск сломать сторонние пользовательские плагины "исподтишка" — они продолжают работать в привычной монотонной модели событий внутри своего процесса.
- Опирается на уже существующий и протестированный код (`Slicer`, `JsonReporter`) — основная работа сводится к оркестрации и мерж-скрипту, а не к переработке ядра.
- Основной минус (overhead старта процессов и отсутствие "из коробки" live-агрегированного вывода) — не критичен для типичного CI-сценария (запуск сьюта целиком раз за пайплайн) и решается точечно (раздел 2, пункт 7 плана 03 — ретрансляция stdout с префиксом воркера).

Рекомендуемая последовательность:
1. Реализовать вариант 03 как MVP — он закрывает практическую потребность "запускать тесты параллельно" быстрее всего и с наименьшим риском.
2. Параллельно (не блокируя п.1) начать вариант 01 как **дополнение**, а не замену — для случаев, где overhead запуска процессов не оправдан (маленькие сьюты, локальная разработка), после того как будут закрыты блокирующие патчи (п. 1, 3, 4, 8 из плана 01).
3. Вариант 02 (sub-interpreters) оставить в бэклоге как R&D — возвращаться к нему только если появятся конкретные CPU-bound кейсы, для которых ни 01, ни 03 не дают приемлемого решения, и только на проектах, готовых зафиксировать минимальную версию Python 3.13+.
